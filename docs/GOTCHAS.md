# Gotchas

Live traps only, one short entry each. The PR that fixes a trap deletes its entry.

- **Claude Review, Size and Attribution run main's copy of their workflow** (`pull_request_target`), so a PR that edits one is checked by the old version; the change takes effect after merge. They don't run at all on the PR that first adds them. Required checks match by name, so a PR could add a decoy workflow with a job named like a gate: reviewers treat any new workflow job named CI gate, Size, Attribution or Claude Review as a blocker (rule break).
- **GitHub silently turns off auto-merge when a required check fails.** Turn it back on after the fix is green.
- **Auto-merge can merge while you're still pushing.** Run `git fetch --prune` before re-pushing a branch; if it already merged, put the new commit on a fresh branch from main.
- **A fresh worktree has no node_modules,** and Node then resolves packages from the main checkout's, checking your branch against main's code. The ensure-deps hook installs them; if it didn't run, `npm ci && npx prisma generate` before the first check.
- **Reviewer subagents must run in the foreground** of the worker's turn; a backgrounded one is lost when the turn ends. Some hosts (the Claude desktop app) start them in the background anyway: then wait for both reports before acting, and never ship on one.
- **In a cloud session `gh pr create` may fail.** Use the GitHub MCP, then strip the footer it adds to the description.
- **One local Postgres serves every worktree** (`docker compose up -d --wait`), and a worktree has no `.env`. Give your branch its own database: `docker compose exec postgres createdb -U fitted fitted_<step>`, then put `DATABASE_URL=postgresql://fitted:fitted@localhost:5432/fitted_<step>` in front of each command that needs it, since every agent shell starts fresh. Branches with different migrations on one database read as drift, and Prisma wants to reset it; a database that doesn't exist yet shows up as P1001, "can't reach database server". The database tests skip without `DATABASE_URL`; CI always runs them.
- **The Write and Edit tools turn `\uXXXX` escapes into the literal character,** so an escape meant for source can land as an invisible BOM or control character. Write escapes with a shell heredoc instead, and check `git diff` for invisible characters.
- **Background workers share one scratch folder.** Give every scratch file a step-specific name (`pr-body-step-<n>.md`), or a parallel worker overwrites it.
- **`shopify app deploy` deletes `include_config_on_deploy` from `shopify.app.toml`.** Leave that edit out of your PR. If deploys don't reach the dev store, an old dev preview is still active there: run `shopify app dev clean`.
- **Only one `shopify app dev` can run for the app at a time.** Parallel workers' dev servers clash, and after a clash dev may start no tunnel and load example.com. Check `pgrep -fl "shopify app dev"` first and wait if one runs; never stop another worker's or start your own tunnel. If dev still won't start, open the PR green and park with the store checks left.
- **The Shopify CLI needs an interactive terminal** for sign-in and prompts. Run it in the owner's terminal, or pass every flag (`--name`, `--flavor`, `--client-id`).
- **`shopify app dev` asks for the storefront password** now that the app has a theme app extension, and dev stores are always password protected. Without it, check the storefront by deploying (`shopify app deploy --allow-updates`) and adding the block in the signed-in admin's theme editor without saving. A deploy releases your branch's whole app, config and extensions, to every store that has it, until the next deploy replaces it. That's safe only while the dev store is the only install; say so on your issue. For a check that needs only the embedded admin, run `shopify app dev` from a scratch copy without `extensions/size-guide/`: no password prompt, and `shopify app dev clean` afterwards.
- **The agent shell may be zsh,** which compares `[[ $f == $glob ]]` as plain text. Run the pipeline scripts by path (their shebang is bash), never by pasting their loops into the shell.
- **Files in `app/routes/` become routes, except tests:** `ignoredRouteFiles` in `app/routes.ts` drops `**/*.test.{ts,tsx}` and must match the Vitest `include` in `vitest.config.ts`. Drift can fail the build, or pass silently: a file that is neither a route nor a test.
- **Board commands need the `project` scope** on the gh login (`gh auth refresh -s project`). Without it, `scripts/issue-status.sh` fails; the issue labels still hold the state. The board's Status options must be exactly Todo, In progress, In review, Parked, Done.
- **Every agent posts to GitHub as the owner.** Owner steering is an untagged comment with `authorAssociation` OWNER in `gh issue view --json`; an agent comment that forgets its `[conductor]` / `[worker step-<n>]` tag would count as steering. The plain-text `--comments` view can be forged by anyone.
